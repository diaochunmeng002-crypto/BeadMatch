### 只有一套规则（2026-09-12 定）

- 移动规则**只有一条**：一次挪一颗，**落点只要有空位就能放** —— 空柱，或柱子上还有位置（未满）。
- **没有**「只能放到空柱，或顶色相同的柱子上」这条限制。需求方第三次强调：文档、生成器、界面、
  求解器用法都不许再出现这条限制。
- 所以乱走时能走的步 = 玩的时候能走的步：把乱走的顺序倒过来，每一步的目标柱都是刚被搬走一颗、
  空出一格的那根，**一定放得回去** ⟹ 乱走出来的局面一定能解开，不需要 solver 兜底。

### 旧模型下的实测（2026-09-11 记录，规则已改，仅供参考）

下面两条都是在「只能放到空柱或同色柱顶」的**旧模型**下做的，**不能当成本项目规则的结论**：

- 6 色 1 空柱、随机摆放：0/30 有解（当时记在 `research.md` 6.3）。
- solver 是纯 Python，大配置判一次最优很慢：6 色 8 柱 23.5 秒（同上）。

**三段结构**

| # | 段 | 规则 |
| --- | --- | --- |
| 1 | 注释区（`#` 开头，图里是前 2 行） | **只写不读**：颜色全名、生成时间。解析时整段忽略（难度不放这儿，见下） |
| 2 | 元信息区（`key=value`） | 要读：`id` / `tubes` / `colors` / `capacity` / `balls_per_color` / `level` / `moves` / `seed` |
| 3 | 网格区 | 每列 = 一根柱子（列数 = `tubes`），每行 = 一个位置（行数 = `capacity`），**第 1 行 = 最顶端**（对应「顶为 0」）；格子里是颜色首字母，`X` = 空位；分隔是「字母 + 一个空格」 |

注：`colors=YGRPBO` 里的字母不含 `X`（`X` 是空位保留符号）；颜色表本身仍然**写死在代码里**（6 个，见待确认项 #10），文件里这行用来做一致性校验。

**函数**：`render_board(matrix) -> str` —— 传入 `矩阵[柱子][位置]`，返回这段文本；
不自己 print（方便测试，也方便以后 web 复用）。要直接打印就再加 `print_board(matrix)` 包一层。

### 题库与题目文件字段（2026-09-12 讨论）

需求方方案：`generator.py` 每跑一次，往**题库文件夹**里产出一个题目文件（一题一文件）。

**为什么这样合适**：出题是家长/老师偶尔做一次的动作，玩是天天玩；文件存下来就能反复用、
人工挑、手工改，等级也能直接从文件读出来，不用每次重算。

**加的字段**（第 2 段 `key=value` 里，都是可读的；**键名一律小写**）：

| 字段 | 例子 | 干什么用 |
| --- | --- | --- |
| `id` | `20260912-100000-3-7f3a` | 题目唯一标识。文件名直接用它；日志、以后"再做第几题"都靠它。**建议用时间 + 随机后缀**，不要用"第 N 题"这种序号（删掉一个就全乱）；id 生成后就不要再变 |
| `level` | `3` | 等级（= 步数 ÷ 10 **向上取整**，0 步 = 0 级）。**从注释区挪到元信息区**，可读：用户想要 3 等级的题，就按它筛 |
| `moves` | `19` | solver 算出的步数。等级是从它换算来的，存下来以后改分档规则（比如改成 15 步一档）不用重跑；也能看出"2 级 = 19 步"这种细节 |
| `seed`（可选） | `12345` | 随机种子，用来复现同一道题 |

**2026-09-12 调整**

- 等级**挪到元信息区**，注释区**不再写** `# Difficulty`（两处重复迟早会不一致）。

### 实测：`unsolved` / `aborted` 到底会不会出现（2026-09-12）

条件：6 色 / 容量 10 / 1 空柱（7 柱），自由乱走 N 步后交给 `ColorSortSolver(single_mode=True)` 判：

| 走多少步 | 结果 |
| --- | --- |
| 10 步 | 3/3 有解：步数 9 / 6 / 7 → 1 级 |
| 100 步 | 3/3 有解：步数 29 / 32 / 36 → 3~4 级 |
| 1000 步 | **2/3 无解**（`unsolved`，步数 0）；1/3 有解，95 步 → 10 级 |

- **`aborted` 一次都没出现**（节点数最大 4973，远没到上限）——这条判断是对的。
- **但 `unsolved` 会出现，而且走得越久越容易**：10 / 100 步时没遇到，1000 步时 3 个里 2 个。
- 原因：solver 认的是**旧规则**；自由乱走时间一长，局面就跑到旧规则解不开的地方去了
  （和当时记在 `research.md` 6.3 的「6 色 1 空柱随机排列 0/30 有解」是同一个现象）。

含义：**必须按 `status` 分支**（见 #22），不能只看步数；另外 `WALK_STEPS` 这个常量直接决定
「出得来题还是出不来」——走得多等级高，但撞上 `unsolved` 的概率也大。

### 能不能把求解器改成我们的规则？（2026-09-12 讨论）

**能改，改动点很小，但改完「最优 / 无解」这两个结论都不能再当真。**

改动点：`solver/kociemba_solver.py` 的 `_apply_move` 里两条判断——
「目标柱未满且顶色不同 → 不合法」（single 版在 [第 352 行](../solver/kociemba_solver.py#L352) 附近，
multi 版在 [第 361 行](../solver/kociemba_solver.py#L361) 附近）。删掉它们，落点判断就只剩「有空位」。

但要注意：

1. `vendor/kociemba/water.pas` 是**原版存档**，不要动；要改就改我们自己的移植版。
2. 改完要重新验证正确性：
   - 它的搜索骨架是「按层 BFS + 哈希去重」，层数就是步数，这部分不依赖移动规则，放宽后框架照跑；
   - 但里面的剪枝（例如「目标空、源柱只有一颗就不搬」）和 single 模式的收尾修正（correction）
     都是为旧规则写的；放宽后会出现「搬进空柱再搬出来」这类绕圈，得重新处理；
   - `unsolved` 的判定是「状态空间搜完还没到目标」。新规则下状态空间大若干量级，
     可能又慢、又搜不完，于是把「解不出」误报成「无解」。
3. **验证手段是现成的**：`solver/test_kociemba_solver.py` 里有一个**独立重写**的暴力 BFS 对拍器。
   把它的移动规则也换成新规则，就能验证改完的求解器算的是不是最优。
4. **最大风险是性能**：旧规则下每步可选走法很少，新规则下分支更多、可达状态爆炸，
   BFS 到 20 步以上很可能算不动。

建议：**另存一份**（例如 `solver/free_solver.py`），不要就地改 `kociemba_solver.py`——
那一份留着当旧规则的参照物和对拍基准，改烂了就没东西可比了。

#### 实测（2026-09-12）：6 色 / 7 柱 / 自由走 200 步 / 3 道题

| # | 下界（至少挪几颗球） | 旧规则 solver | 按我们的规则 BFS（60 秒上限） |
| --- | --- | --- | --- |
| 1 | 23 步 | near-optimal，45 步，758 节点，**0.05s** | 只搜到第 **6** 层，441k 节点，60s，**没搜完** |
| 2 | 26 步 | near-optimal，35 步，432 节点，**0.03s** | 只搜到第 **7** 层，438k 节点，60s，**没搜完** |
| 3 | 23 步 | **unsolved**，0 步，532 节点，0.08s | 只搜到第 **6** 层，378k 节点，60s，**没搜完** |

结论：

- **旧规则 solver 秒出**（0.03~0.08 秒），200 步的题基本还解得动（3 道里 2 道）。
  代价是它算的是**旧规则**下的解（45 / 35 步），不是我们的规则。
- **按我们的规则算最优：算不动。** 60 秒只搜到第 6~7 层，而题目至少 23 步、
  旧规则参考解 45 步；每层大约 10 倍增长，差着十几个数量级，不是调参能解决的。
- 真最优落在 **[下界, 旧规则步数]** 这个区间里（例：第 1 题在 [23, 45]）。

### 自研求解器：第一版怎么写（2026-09-12 讨论）

**结论：能写，而且第一版就写 DFS + 启发式；不要写 BFS 求最优（已经实测否掉了）。**

外面那份 AI 建议里说「如果随机 200 步 → BFS 0.3 秒 → 最优 47 步，那就很爽；
如果 30 分钟爆内存再换算法」——**我们已经在上面实测过了，是后者**：
6 色 / 7 柱 / 200 步，BFS 60 秒只搜到第 6~7 层（约 40 万节点），而题目至少 23 步。
每层约 ×10，搜到 23 层差十几个数量级。所以「先写 BFS 拿最优」不用再试。

**为什么 DFS + 启发式够用**：

- 我们要的不是「最优」，是「一个稳定的难度数字」+「第 3 条 `next()` 能用的走法」。
- DFS 找到可行解就返回；配合启发式排序，实际局面上通常很快就出解。
- 它给的解长度是**上界**（真最优落在 `[下界, 这个解]` 之间），比旧规则 solver 的数更贴近我们的规则。

**第一版设计（讨论稿）**

```
solve(state, max_depth = 300):
    if is_finished(state): return []
    seen = set()
    return dfs(state, [], seen, max_depth)

dfs(state, path, seen, budget):
    if is_finished(state): return path
    if len(path) >= budget: return FAIL
    key = canon(state)                 # 柱子排序后去重（消除空柱位置差异）
    if key in seen: return FAIL
    seen.add(key)
    for move in score_sorted(legal_moves(state)):
        r = dfs(apply(state, move), path + [move], seen, budget)
        if r is not FAIL: return r
    return FAIL
```

启发式打分（沿用外部建议的思路，删掉两条不必要的）：

- 让某颜色更集中：**+**
- 完成一根柱子（整柱同色，且该色全部在这一柱）：**+++**
- 破坏一根已经完成的柱子：**−−−**（我们的规则下，完成的柱子永远不用动）
- `A → B → A`：**不用特意扣分**，`seen` 已经挡住同一局面重复进入

**`is_finished` 要按 2.3 的新措辞写**：每根柱子要么空，要么**整根同色，且该颜色的球全部在这一根柱子上**。
外部那份伪代码只检查了「整柱同色」——按我们改过的 2.3，一种颜色被拆成两根单色柱（比如 6 颗 + 4 颗）
也会被误判成完成，这是错的。

**对拍**：DFS 的正确性（解合法、确实能走到终局）可以用小规模暴力 BFS 验证——
`solver/test_kociemba_solver.py` 里那个独立实现，把移动规则换成我们的就行。

**附带收益**：这个求解器同时把第 3 条 `next()` 解决了——「下一步怎么走」就是「求一条解，返回第一步」。
这也是现成 solver 帮不上的地方（它按旧规则给的走法，在我们的规则下虽然合法，
但它可能根本找不到解，甚至误报无解）。
