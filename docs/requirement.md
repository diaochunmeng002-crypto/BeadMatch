## 1. 这是什么

实体玩具：木质底座上竖着若干根立柱，玩家把彩色木珠一颗颗串上去。
参考状态：6 种颜色各占一根立柱（珠子按颜色归好类），底座上留一根空柱。

软件要做的：**生成初始局面**，让小孩照着在实物上把珠子摆好，然后开始玩。

> 软件**不负责解题**，它只负责「出题」和「告诉人怎么摆」。

现在其实有两块东西了：

- **出题器**（离线）：`generator.py` 出单道、`make_puzzles.py` 批量出，产出 `puzzles/` 题库；
- **网页**（玩的时候）：FastAPI 后端 + `web/` 前端，从题库抽题、渲染、读颜色、演示解法。

## 2. 游戏规则

### 2.1 棋盘

- 由若干根**立柱**组成，竖在底座上。
- 每种颜色珠子总数相同，本玩具为 **10 颗**；每根立柱最多串 **10 颗**。
- 开局留有空柱作为周转空间。

### 2.2 移动规则

- 一次只能移动**某根立柱最顶上的一颗**珠子。
- 目标立柱**只要有空位就能放**：空柱，或者还没串满的立柱。
- **没有**「只能放到顶色相同的柱子上」这类限制。

> 这条是 2026-09-12 需求方第三次强调后定下的：全项目（文档、生成器、界面、求解器用法）
> 都不许再引入「只能放空柱或同色柱顶」的限制。
> 注意这跟**商业球排序游戏**（以及 `solver/kociemba_solver.py` 实现的模型）**不是同一套规则**，
> 详见 `§8 求解器`。

### 2.3 胜利条件

- **每种颜色全部集中在一根立柱上**，其余立柱空着。

> 2026-09-12 修订：原文是「每根立柱要么空着，要么整根同色」。按字面，
> 一种颜色拆成两根单色柱（6 颗 + 4 颗）也算赢，那不是本意。

### 2.4 死局

**不存在。** 珠子总数（6 色 × 10 = 60 颗）少于总容量（7 柱 × 10 = 70 格），
永远至少空 10 格，所以「没有任何合法移动」的情况不会出现。

## 3. 参数

### 3.1 全局参数

```python
tubes           = 7    # 柱子数
colors          = 6    # 颜色数
balls_per_color = 10   # 每色珠子数
capacity        = 10   # 每根柱子的容量（能装几格）
WALK_STEPS      = 100  # 出题时随机乱走多少步（见 §4）
```

**`capacity` 和 `balls_per_color` 不是一回事**：

| 参数 | 管什么 | 现在 |
| --- | --- | --- |
| `balls_per_color` | 一种颜色**一共几颗**（颜色维度） | 10 颗 |
| `capacity` | 一根柱子**最多装几格**（柱子维度） | 10 格 |

珠子总数 = `colors × balls_per_color` = **60 颗**；格子总数 = `tubes × capacity` = **70 格**。
两个值都等于 10，才有「一种颜色正好装满一根柱子」这个巧合。

用在哪：网页网格的**列数**由 `tubes` 决定、**行数**由 `capacity` 决定；
`balls_per_color` 不参与排版，只决定每种颜色有几颗（也用于校验）。

约束：`capacity ≥ balls_per_color`，否则一种颜色装不进一根柱子。

### 3.2 颜色表（写死，不让改）

| 编号 | 字母 | 英文名 | 中文名 |
| --- | --- | --- | --- |
| 1 | `Y` | Yellow | 黄 |
| 2 | `G` | Green | 绿 |
| 3 | `R` | Red | 红 |
| 4 | `P` | Purple | 紫 |
| 5 | `B` | Blue | 蓝 |
| 6 | `O` | Orange | 橙 |

- `X` = **空位**，是保留符号，颜色名不得以 X 开头。
- 编号顺序就是上面这个顺序（`YGRPBO`），代码里是常量。

### 3.3 难度等级

**等级 = 步数 ÷ 10 向上取整**，即 `(moves + 9) // 10`：

| 步数 | 等级 |
| --- | --- |
| 0 | 0 级 |
| 1 ~ 10 | 1 级 |
| 11 ~ 20 | 2 级 |
| 21 ~ 30 | 3 级 |
| …… | 无上限 |

不再用「易 / 中 / 难」三档。步数取「解决这道题所需的最少挪动步数」
（当前实际用的是求解器给的值，见 `§8`）。

### 3.4 硬性约束

- **柱子数 ≥ 颜色数 + 1**，否则摆不开。当前 7 柱 6 色 = 1 根空柱。
- 生成的局面**必须有解**（当前实现里由生成方式保证，见 `§4.1`）。
- 每种颜色固定 10 颗。
- 柱子数 / 颜色数的上下限是代码常量，不做在界面上。

> **悬而未决的一条**：早期用旧规则实测出「6 色 + 7 柱随机局面 0/30 有解」，
> 据此认为空柱至少要 2 根，与当前参数上限冲突。但**换成新规则后这个结论已经不适用**
> （新规则下随机排列也不会卡死），所以参数上限维持 7 柱 / 6 色，等难度问题一起再看（`§9`）。

## 4. 出题

### 4.1 方式

**从已解局面按 §2.2 的规则随机乱走 N 步**（N = `WALK_STEPS`，默认 100）：

```
已解局面 ──随机走 N 步（落点只要有空位）──▶ 初始局面
         ──交给求解器求一条解──▶ 步数 → 等级
```

产物写进题库（`§5.6`）。`generator.generate(difficulty=5, *, seed, puzzle_id, walk_steps)`
返回 `(矩阵, 元信息)`，**自己不落盘**；落盘交给调用方。

`difficulty` 参数目前**不参与筛选**（出什么收什么），只保留接口。

生成是确定性的：同一组 `steps + seed` 必然复现同一道题。

### 4.2 收题规则（`make_puzzles.py`）

1. 解不出来 → 不收；
2. 解的长度 > **下界 × 2** → 判为「绕远路的解」，**直接丢弃**（`--ratio-max` 可调）。

### 4.3 实测（2026-09-13，100 步 ×500 + 200 步 ×100）

| | 乱走 100 步 ×500 | 乱走 200 步 ×100 |
| --- | --- | --- |
| 解出率 | 79% | 53% |
| **收进题库** | **364** | **45** |
| 收下的步数 min/avg/max | 11 / 26.0 / 45 | 21 / 35.8 / 50 |
| 等级分布 | 2 级×54、3 级×233、4 级×73、5 级×4 | 3 级×12、4 级×19、5 级×14 |
| 用时 | 614 秒 | 252 秒 |

两轮共解出 447 道，38 道因「解太长」被丢弃，最后收下 **409 道**。
原始数据在 `puzzles/index.csv`。

结论：**日常用 100 步**（出题多、等级 2~4）；要高等级用 200 步，但成功率只有一半，适合离线批量。

### 4.4 已知问题：题面偏「整齐」，实际难度偏低（2026-09-14）

对现有 409 道题全量统计：

| 指标 | 最小 | 平均 | 最大 |
| --- | --- | --- | --- |
| 最长同色连续段 | 6 | **8.0** | 10（=柱子容量） |
| 不在位的球（下界） | 10 | 19.4 / 共 60 颗 | 28 |
| 每根柱子的平均颜色种数 | 2.0 | **2.9** / 共 6 种 | 3.9 |

最长同色段分布：`6→3 道，7→79，8→246，9→79，10→2`。
也就是**几乎每道题都有一根 8~10 颗的纯色柱**，孩子一眼就能看出该往哪搬。

原因三条：

1. 生成方式是「从已解状态随机走」，每步只搬一颗球、还经常互抵，
   所以只有 1/3 的球真正离开了原位，其余仍连成长段；
2. **步数和「要不要动脑」脱钩**：长段压在底下，要放散珠就得先挪开挡路的球，
   步数被「搬开—搬回」撑起来，所以 5 级也可能是「看着简单」；
3. **更根本**：§2.2 的规则比商业球排序宽松（任意有空位都能放），
   理论上不存在会卡住的局面，难度天花板就在那儿。

候选方案见 `§9#1`。

## 5. 数据格式（题库文件）

### 5.1 样子

```
# colors: Yellow Green Red Purple Blue Orange

created_at=2026-09-13 00:09:17
created_by=beadmatch
solution_by=kociemba
id=20260913-000917-971c
tubes=7
colors=YGRPBO
capacity=10
balls_per_color=10
level=2
moves=19
seed=2
steps=100
generator=random_walk@1
solution=2-4 5-4 6-4 6-4 5-6 5-3 2-5 2-3 7-2 7-4 7-2 1-4 1-4 7-1 7-5 7-5 7-2 7-6 7-1

P P X X P P X
P B X X O P G
Y R R X R O P
Y G R X B O G
Y G R X B O Y
Y G R X B O B
Y G R X B O B
Y G R P B O G
Y G R P B O O
Y G R P B O Y
```

### 5.2 三段结构

| 段 | 内容 | 读不读 |
| --- | --- | --- |
| 注释区：所有以 `#` 开头的行 | 给人看的（颜色全名） | **只写不读**，解析时整段忽略 |
| 元信息区：`key=value`（**键名一律小写**） | 见 5.3。**前三行固定是 `created_at` / `created_by` / `solution_by`** | 读 |
| 网格区：`capacity` 行 × `tubes` 列 | 局面 | 读 |

### 5.3 字段

| 字段 | 例子 | 说明 |
| --- | --- | --- |
| `created_at` | `2026-09-13 00:09:17` | **什么时候生成的**（正文第一行）。格式固定 `YYYY-MM-DD HH:MM:SS`，读入时校验 |
| `created_by` | `beadmatch` | **谁出的**（正文第二行）：生成工具的名字；以后手工摆的题可以写 `manual` 或人名 |
| `solution_by` | `kociemba` | **这条解是谁给的**（正文第三行）：`kociemba` = 现成的旧规则求解器（现在这 409 道全是它）；`dfs` = 我们自己的兜底求解器（给过 129/170 步的绕路解，都被收题规则丢了）；以后可能是 `walk`（反走即解）。**可选**，格式同 `generator` |
| `id` | `20260913-000917-971c` | 题目唯一标识：**时间 + 随机后缀**。文件名直接用，生成后不再变。不要用「第 N 题」这种序号，也不要把等级写进 id |
| `tubes` | `7` | 柱子数 = 网格列数 |
| `colors` | `YGRPBO` | 本题用到的颜色字母（**不含 `X`**） |
| `capacity` | `10` | 每根柱子容量 = 网格行数 |
| `balls_per_color` | `10` | 每种颜色几颗 |
| `level` | `2` | 难度等级（见 3.3）。按等级挑题就靠它 |
| `moves` | `19` | 求解器给的步数，等级由它换算 |
| `seed` | `2` | 随机种子（可选） |
| `steps` | `100` | 出题时乱走了多少步（可选）。**复现要 `seed` + `steps` 两个** |
| `generator` | `random_walk@1` | **用哪套算法生成的**：名字 + 版本（算法一改语义就变，所以带版本）。目前的生成器叫 `random_walk`（从已解局面随机走），版本 `1`。**可选**（老文件没有也能读）；以后换算法就写新名字，比如 `reverse_walk@1` |
| `solution` | `2-4 5-4 6-4 …` | **标准解法**：空格分隔的「源柱子-目标柱子」，柱子编号**从 1 起**（和网格第 1 列对齐）。读入时会套回去验证 |

### 5.4 网格规则

- 每列 = 一根柱子（列数 = `tubes`），每行 = 一个位置（行数 = `capacity`）。
- **第 1 行 = 最顶端那一格**，与视觉一致（全项目统一「**顶为 0**」）。
- 柱子没满时，空位在前，珠子在后面；`位置 = capacity - 1` 是最底下那颗。
  例：容量 5、从下到上 红蓝绿 → `[0, 0, 绿, 蓝, 红]`；空柱 → `[0, 0, 0, 0, 0]`。
- 格子是颜色首字母，`X` = 空位，分隔是「字母 + 一个空格」。
- 难度**只写在元信息区**，注释区不重复写（两处写迟早不一致）。

### 5.5 解析与校验

解析（`parse_board`）：

- 忽略**所有** `#` 开头的行（不只前几行）、忽略空行、忽略行尾空白；
- 元信息**按键名取值，不依赖顺序**（以后加字段不破坏兼容）；
- 网格按任意空白切分；编码 UTF-8。

读入即校验，对不上就报错（不能默默读进来）：

- 网格行数 == `capacity`、列数 == `tubes`；
- 空位必须是每根柱子的前缀（不能出现「珠子上面还有空位」）；
- `colors=` 的字母集合 == 网格里实际用到的颜色集合；
- 每种颜色珠子总数 == `balls_per_color`；
- `level` == `(moves + 9) // 10`；
- `id` 与文件名一致；
- `solution` 的步数 == `moves`，**而且套回这道题要真的能解开**。
- `created_at`（如果写了）：必须是 `YYYY-MM-DD HH:MM:SS` 格式；
- `generator` / `created_by` / `solution_by`（如果写了）：只校验格式（字母数字和 `_ @ . + -`，最长 64），
  **不限定取值** —— 这样以后用新算法生成的题，老代码照样能读。

### 5.6 台账与目录

```
puzzles/
├─ index.csv          每道题一行（含没收下的，keep=0）
├─ 2/<id>.txt         等级 2 的题
├─ 3/<id>.txt
└─ …
```

- 一题一文件，文件名 = `<id>.txt`；**不静默覆盖**同名文件。
- **目录就是索引**（2026-09-14 改）：等级看目录名、id 看文件名，后端 `list_levels` / `list_puzzles` /
  `find_puzzle_path` 直接扫目录（409 道全扫约 20 毫秒）。**题库的唯一真相是这些题目文件本身**，
  不再依赖任何台账。
  （原因：之前读 `index.csv`，结果 `POST /api/generate?save=true` 新存的题不会出现在接口里——
  台账和文件打架。回归测试见 `server/test_app.py::test_saved_puzzle_shows_up_immediately`。）
- `index.csv` 现在只是**批次日志**（`make_puzzles.py` 仍在写，代码不再读它）；以后计划挪到 `logs/`。
  它的列：`series, seed, ok, keep, source, moves, level, lower_bound, ratio, seconds, id, generator, created_by, path`。
- 单道出题：`python generator.py`；批量：`python make_puzzles.py`。

### 5.7 函数（`generator.py`）

| 函数 | 作用 |
| --- | --- |
| `generate(difficulty=5, *, seed, puzzle_id, walk_steps, attempts)` | 出一道题，返回 `(矩阵, 元信息)`，**不落盘** |
| `render_board(matrix, meta=None)` | 给 `meta` 出完整三段式（题目文件内容）；不给只出网格（调试用） |
| `parse_board(text)` | 反向解析，返回 `(矩阵, 元信息)` |
| `load_board(path)` / `save_board(path, matrix, meta)` | 读 / 写题目文件（写时按等级分文件夹） |
| `print_board(matrix, meta=None)` | 打印的壳 |
| `list_levels(root)` / `list_puzzles(root, level)` / `find_puzzle_path(root, id)` | 题库索引（后端用） |

自测：`parse_board(render_board(m, meta)) == (m, meta)`，存文件再读回来一模一样。

## 6. 后端（FastAPI）

职责很小：**把题库读出来给前端 + 算「下一步」+ 需要时现出一题**。
出题和求解都在 Python 侧（`generator.py` / `solver/free_solver.py`），后端只做包装。

`server/app.py`；跑：`python -m server.app`（默认 `127.0.0.1:8000`）；文档：`/docs`。

| 接口 | 作用 |
| --- | --- |
| `GET /api/health` | 活着没 + 题库目录 |
| `GET /api/levels` | 每个等级各多少道题 |
| `GET /api/puzzles?level=3` | 列出题目（可按等级筛） |
| `GET /api/puzzles/{id}` | 取一道题：`matrix` + `solution` + 元信息 |
| `GET /api/random?level=3` | **从某一个等级里随机抽一道**（`level` 必填） |
| `POST /api/next {matrix}` | **暂定接口**（第 3 条未定稿）：提示下一步，返回第一步 + 剩余步数 + 整条解 |
| `POST /api/generate {difficulty, walk_steps, seed, save}` | 现场出一题（默认不落盘） |
| `POST /api/play {matrix}` | 算整条解（给「演示解法」动画用） |

- 入参会校验（行列数、颜色取值、空位在顶端、每色颗数），对不上返回 400。
- **题库靠扫目录**（不读台账）：`/api/levels` 数 `puzzles/<等级>/` 里的文件，
  `/api/puzzles` 只读每道题的**文件头**拿 `level` / `moves`。所以新存一道题，
  下一次请求就能看到，不需要改任何索引。
- 前端静态文件放 `web/`：起服务时挂到 `/static`，`web/index.html` 存在时根路径直接返回它。

## 7. 前端（`web/`）

**原生 JS，不引框架、不用构建**（理由：动画/声音/朗读都是命令式操作，框架收益低；
三个文件离线可跑）。当前版本：

- 难度下拉（`/api/levels`）+「换一题」（`/api/random?level=N`）
- 柱子和球用 CSS 画；**出题时球一颗颗落下**
- **点柱子**：从上到下读出颜色（气泡文字 + 可选语音）
- **「演示解法」**：按题目 `solution` 一步步飞球（FLIP 动画）+ 落珠声，最后「叮」
- 音效（Web Audio 合成，无音频文件）/ 朗读（`speechSynthesis`，zh-CN）各有开关
- 支持 `prefers-reduced-motion`；静态文件取不到时首页会弹红条自我诊断

## 8. 求解器

### 8.1 两套规则

- **我们的规则**（§2.2）：落点只要有空位。`solver/free_solver.py` 实现这套。
- **旧规则**（商业球排序 / `solver/kociemba_solver.py` 的原版模型）：只能放空柱或同色柱顶。
  `vendor/kociemba/` 是原版存档，不参与运行，**也不随仓库分发**（`.gitignore` 里排除了）。

两套规则的关键差别：

- 旧规则下**会走死**，所以有难度；我们的规则下永远不会卡死。
- 旧规则的走法在我们规则下**同样合法**，所以它能给出解时可以直接拿来用（还很快：0.03~0.08 秒）；
  但它的「最优步数」在我们的规则下只是**上界**，它报「无解」也不代表我们的题解不开。

### 8.2 `free_solver.py`

| 函数 | 说明 |
| --- | --- |
| `solve_any(state)` | 先用 `kociemba_solver`（旧规则）求短解，它给不出再用 `solve` 兜底 |
| `solve(state, ...)` | 我们自己的求解器：**随机化贪心 DFS + 启发式**（先给每种颜色定一个「家」，按「搬完离目标更近」排序，一条路走不通就换顺序重开）。**只保证能解开、不保证步数最少** |
| `verify(state, moves)` | 把走法套回局面，检查是否真的解开 |
| `format_moves` / `parse_moves` | `3-7 1-2` 格式（1 起）与内部 `(i, j)`（0 起）互转 |
| `is_finished` / `legal_moves` / `apply_move` | 规则判定与走法 |

实测（2026-09-13）：`solve_any` 在 100 步的题上 5/5 成功、平均 0.04 秒；
200 步的题只有 3/5。**我们自己的 DFS 单独用会绕远路**（出现过 129 / 170 步的解），
所以它的定位只是兜底。
